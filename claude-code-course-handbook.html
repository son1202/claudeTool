1-1 Coding Agent 到底替你做什麼補充

聊天式 AI 給你一段程式碼，剩下的整合、執行、除錯還是你做。Coding Agent 的差別在於它自己跑完一個迴圈：蒐集脈絡、採取行動、驗證結果，不對就再來一輪。

  • 蒐集脈絡：用搜尋與讀檔工具自己找出相關檔案，不需要你逐個貼上。
  • 採取行動：直接改檔、建檔、在你的終端機執行指令（編譯、跑測試、git 操作）。
  • 驗證結果：讀取編譯錯誤或測試輸出，據此修正。

適合交出去的工作：熟悉陌生 codebase、實作定義清楚的功能、修有重現步驟的 bug、補測試、重構、寫 commit 與 PR 描述。需要你把關的部分：需求是否正確、架構取捨、以及任何不可逆的操作。

1-2 設計理念：和其他 AI 工具差在哪補充

試閱影片的檔名顯示這個單元拿 Copilot 與 Jules 做比較。三類工具的定位可以這樣分：

類型代表運作位置你的角色
行內補全GitHub Copilot 補全編輯器游標處你寫，AI 接話
雲端非同步 AgentGoogle Jules遠端 VM，交付 PR派工後等結果
本地終端 AgentClaude Code你的機器、你的 shell即時協作、隨時打斷

Claude Code 的幾個設計選擇：

  • 活在終端機：你的工具鏈（編譯器、測試、git、部署腳本）它都能直接用，不必另外整合。
  • 低階、不預設流程：它給的是原始能力，工作流由你用 CLAUDE.md、指令、Hook、Sub-Agent 組出來。這也是整門課後四章的主線。
  • 可組合：遵循 Unix 哲學，claude -p 可接在 pipe 裡、放進腳本或 CI。
  • 權限預設保守：改檔與執行指令前會詢問，由你逐步放寬。

1-6 作業：超級食物與穿牆模式補充

這份作業練的是「在既有程式碼上迭代」，和從零生成是不同的技能。建議做法：

  1. 先請 Claude 讀現有程式並說明遊戲主迴圈與碰撞判定在哪裡，確認它看懂。
  2. 把規則寫成可驗收的條件：超級食物多久出現一次、存在幾秒、加幾分、長什麼樣；穿牆模式怎麼切換、從左邊出去是否從右邊同一列進來。
  3. 一次只加一個機制，測過、commit，再做下一個。
  4. 留意邊界：穿牆時食物生成位置、穿牆瞬間的自撞判定、兩個機制同時生效的情況。

2-1 核心能力總覽：常用指令與使用情境補充

Claude Code 的操作介面只有三種輸入：自然語言、斜線指令、快捷鍵。先記住依情境分組的這幾個就夠用：

情境指令或按鍵
剛進一個專案/init、/memory、/permissions
給脈絡@路徑、貼上圖片
控制節奏Shift+Tab 切換模式、Esc 打斷
管理脈絡/context、/compact、/clear、/rewind
接續工作claude -c、claude -r、/resume
不知道有什麼/help，或輸入 / 看清單

另外兩個前綴：! 開頭直接執行 shell 指令並把輸出帶進對話；# 開頭可把一句話快速記進 CLAUDE.md（新版行為可能調整，以 /help 為準）。

使用情境大致四類：問 codebase 問題（「登入流程從哪裡開始？」）、改程式、跑指令與除錯、git 操作。第一類最被低估，進陌生專案先問問題，比直接叫它改安全得多。

2-2 【INIT】CLAUDE.md 初始化補充

/init 會掃描專案後產生 CLAUDE.md 初版。這份檔案在每次對話開始時自動載入，等於專案的「到職說明」。用 /memory 檢視與編輯。

位置範圍放什麼
./CLAUDE.md專案，進 git 與團隊共用建置與測試指令、目錄結構、程式風格、禁區
./CLAUDE.local.md專案，僅自己個人測試環境、本機路徑
~/.claude/CLAUDE.md你的所有專案個人偏好，例如回覆語言、commit 風格
 
# CLAUDE.md 範例
## 指令
- 建置：npm run build
- 單一測試：npm test -- path/to/file.test.ts
- 改完程式一律跑 npm run typecheck

## 架構
- src/api 是 Express 路由，src/db 是 Prisma，src/web 是 React
- 詳細 API 規格見 @docs/api-spec.md

## 規則
- 不要修改 migrations/ 下已存在的檔案
- 新功能必須附測試

/init 產生的內容只是起點，通常偏長偏泛，要自己刪改。原則：短、具體、可檢查。每一行都佔脈絡，「保持程式碼整潔」這類句子沒有作用。之後發現 Claude 重複犯同一個錯，就補一條規則。

2-3 【@FILE】檔案參照：用 Context 取代冗長 Prompt補充

與其用三段文字描述「那個處理登入的檔案裡的驗證邏輯」，不如直接指給它看。@ 後面接路徑，支援 Tab 補全，檔案內容會直接進入對話。

# 冗長又不精確
幫我做登出功能，風格要跟登入一樣，登入在 auth 資料夾裡面那個...

# 用參照
參考 @src/auth/login.ts 的結構與錯誤處理，實作 logout，
路由加在 @src/routes/auth.ts
  • @目錄/ 帶入的是目錄列表，不是所有檔案內容。
  • 參照的檔案若所在目錄有自己的 CLAUDE.md，也會一併載入。
  • 只參照需要的。一次丟十個檔案，等於沒有指路。
  • 範本效果最好：「照 @某檔 的模式寫」比任何文字描述的風格要求都可靠。

2-4 【IMAGE】圖片輸入補充

輸入方式：把圖檔拖進終端機、用 Ctrl+V 貼上剪貼簿的圖（macOS 也是 Ctrl 不是 Cmd），或直接給圖檔路徑。

值得用圖的情況：

  • 設計稿轉實作：貼 Figma 截圖，請它照著切版。
  • 視覺 bug：「按鈕跑版了」不如一張截圖。
  • 錯誤畫面：瀏覽器 console、手機上的錯誤訊息。
  • 圖表與架構圖：白板照片、ER diagram、時序圖。
  • 前後對照：改完後再截一張貼回去，請它比對設計稿找差異。

圖片也佔脈絡，裁切到相關區域再貼。第 3 章的 Playwright MCP 則是讓它自己截圖，把這個迴圈自動化。

2-5 作業：滑鼠移到寶箱時變成鑰匙圖示補充

題目強調「用一句 Prompt」，練的是 2-3 與 2-4 的組合：脈絡給對了，prompt 就可以很短。

滑鼠移到 @src/components/TreasureChest.tsx 的寶箱上時，
游標改用 @assets/key.png，離開時恢復。

這句話能成立，是因為兩個 @ 已經把「改哪裡」和「用什麼」講完了。技術上通常是 CSS 的 cursor: url(key.png) x y, pointer，要注意的細節：

  • 游標圖檔尺寸建議 32×32，過大瀏覽器會忽略。
  • url 後面的兩個數字是熱點座標（鑰匙尖端對準的位置），以及一定要有後備值如 pointer。
  • 若寶箱畫在 Canvas 裡而非 DOM 元素，就得在 mousemove 做命中判定後切換 canvas 的 cursor 樣式。

做完貼截圖請 Claude 確認，順便練 2-4。

2-6 【COMPACT】濃縮重點，避免 Context 爆炸補充

脈絡視窗有上限，而且每次請求都會重送整段對話。對話越長，越慢、越貴，前面的指示也越容易被稀釋。

  • /context：先看視窗被什麼佔用（系統提示、MCP 工具、CLAUDE.md、對話）。
  • /compact：把歷史對話摘要成重點後繼續。可以附指示：
    /compact 保留資料表設計的決定與尚未完成的三個 TODO
  • /clear：整個清空。換到不相關的任務時用這個，不要用 compact。
  • 接近上限時會自動壓縮，但自動摘要不知道什麼對你重要，所以在任務告一段落的自然斷點主動 compact 比較好。

更穩的做法是把重要決定寫進檔案（規格、進度 markdown），讓它不依賴對話記憶。摘要會丟細節，檔案不會。

2-7 【REWIND】回到完美的那一刻補充

Claude Code 在你每次送出 prompt 時建立 checkpoint，並在每次改檔前快照。連按兩次 Esc 或輸入 /rewind，選擇要回到哪一則訊息，可以還原：

  • 只還原程式碼（保留對話，讓它知道剛剛走錯了）
  • 只還原對話（保留程式碼，把走偏的討論丟掉）
  • 兩者一起

它同時是脈絡管理工具：一段失敗的嘗試留在對話裡會持續干擾後續判斷，rewind 掉比叫它「忘記剛剛那個」乾淨。

限制：checkpoint 只追蹤 Claude 用編輯工具改的檔案，不追蹤 Bash 指令造成的變更（刪檔、migration、套件安裝），也只存在於該工作階段。它不能取代 git，每完成一個可運作的階段就 commit。

2-8 【RESUME】把每一次對話變成資產補充

對話紀錄依專案目錄存在本機，關掉終端機不會消失。

claude -c          # --continue：接續這個目錄最近一次對話
claude -r          # --resume：從清單挑選歷史對話
/resume            # 在對話中切換到其他歷史對話
  • 接續時完整歷史都會載回來，包含當時的工具呼叫結果。
  • 一個任務一個對話，並用 /rename 取個認得出來的名字，之後才找得到。
  • 適合接續的情況：昨天做到一半的功能、等 CI 結果回來後繼續修。
  • 不適合的情況：對話已經很長很亂。這時請它把現況寫成交接筆記，開新對話用 @ 讀進來，比拖著舊脈絡有效。

真正能累積成「資產」的是沉澱出來的東西：對話中發現的規則寫回 CLAUDE.md，重複的流程做成 Skill（第 4 章）。

2-9 【PLAN MODE】先對齊思路，再動手寫 code補充

按 Shift+Tab 循環切換到 Plan Mode（或用 /plan）。此模式下 Claude 只能讀、不能改檔或執行有副作用的指令，它研究 codebase 後提出計畫，你核可才開始實作。

  1. 探索：請它讀相關檔案，先不要寫程式。
  2. 規劃：產出計畫。在這一步修正方向成本最低，直接回覆要改哪裡即可。
  3. 實作：照計畫執行，要求邊做邊驗證。
  4. 提交：請它寫 commit 與 PR 描述。

審計畫時看三件事：它打算動哪些檔案（範圍是否超出預期）、有沒有誤解需求、打算怎麼驗證。跳過規劃直接叫它寫，是「能生成但跑不起來」最常見的原因。單行修改、改錯字這類小事則不需要。

2-10 【ULTRA THINK】深度推理模式補充

做法是在 prompt 裡加入 think、think hard、ultrathink 這類字眼，讓模型在回答前花更多推理預算。較新的版本改以 /effort 與模型設定調整推理量，關鍵字的行為在版本間變動過，請以你安裝的版本為準。

適合深度推理的問題：

  • 架構決策與多方案取捨
  • 難重現的 bug：race condition、記憶體問題、跨模組的狀態錯亂
  • 牽涉多個檔案的重構或 migration 規劃
  • 安全性與邊界條件審查

和 Plan Mode 搭配效果最好：在規劃階段深想，實作階段不必。改名、補樣板這類工作開深度推理只是多花時間與 token。

2-11 【AUTO MEMORY】Cross-Session 記憶補充

CLAUDE.md 是你寫給 Claude 的；Auto Memory 是 Claude 自己寫給未來的自己的筆記。它在工作中學到的東西（建置指令的坑、你糾正過它的事、除錯心得）會自動存成 markdown，下次在同一個專案開新對話時載入。

  • 存放位置在個人目錄下、依專案分開（~/.claude/projects/<專案>/memory/），不進 git，只屬於你這台機器。
  • 入口檔 MEMORY.md 的開頭部分會在每次對話載入，其餘主題檔按需讀取。
  • 用 /memory 可以瀏覽、編輯、開關這項功能。它就是純文字檔，寫錯了直接改或刪。
  • 也可以明說：「記住：這個專案的整合測試要先啟動 docker compose」。

3-2 MCP 是什麼補充

Model Context Protocol 是開放協定，讓 AI 應用用統一方式連接外部工具與資料，常被比喻為 AI 的 USB-C。Claude Code 是 client，每個外部能力是一個 server，寫一次 server，所有支援 MCP 的 AI 應用都能用。

server 可以提供三種東西：

  • Tools：可呼叫的動作，例如點擊網頁、查詢錯誤、產生圖片。由模型決定何時呼叫。
  • Resources：可讀取的資料，在 Claude Code 裡用 @ 參照。
  • Prompts：預寫好的提示範本，會以斜線指令形式出現。

傳輸方式：本機程序走 stdio；遠端服務走 HTTP（Streamable HTTP，以及較舊的 SSE）。

3-10 【MCP Server】打造你的第一個客製化 MCP Server補充

值得自己寫的時機：公司內部系統沒有現成 server，或想把一段自有腳本變成 AI 可呼叫的能力。官方提供 Python 與 TypeScript SDK，Python 最小範例：

# server.py    安裝：pip install "mcp[cli]"
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("my-tools")

@mcp.tool()
def word_count(text: str) -> dict:
    """計算文字的字數與行數。text 為要分析的內容。"""
    return {"chars": len(text), "lines": text.count("\n") + 1}

if __name__ == "__main__":
    mcp.run()   # 預設走 stdio
claude mcp add my-tools -- python /絕對路徑/server.py

# 不經過 Claude、單獨測試 server
npx @modelcontextprotocol/inspector python server.py

  • stdio server 的 stdout 是協定通道，print() 除錯訊息會弄壞通訊，log 一律寫 stderr。
  • 回傳精簡的結構化資料；工具數量少而精。

3-11 作業：擴充 MCP Server，實作圖片去背工具補充

在 3-10 的 server 加一個工具。Python 用 rembg 套件可以在本機完成去背，不需要外部 API：

# pip install rembg pillow
from pathlib import Path
from PIL import Image
from rembg import remove

@mcp.tool()
def remove_background(input_path: str, output_path: str) -> str:
    """移除圖片背景並輸出透明 PNG。
    input_path、output_path 皆為絕對路徑，output_path 需以 .png 結尾。"""
    src = Path(input_path)
    if not src.is_file():
        return f"錯誤：找不到檔案 {input_path}"
    remove(Image.open(src)).save(output_path)
    return f"完成：{output_path}"

設計上的選擇：傳檔案路徑而不是圖片內容，避免把整張圖的 base64 塞進脈絡。第一次執行會下載模型檔，時間較長屬正常。改完 server 程式後要重啟 Claude Code 或在 /mcp 重新連線才會生效。放在 Toy Marketplace 的情境，就是「幫商品圖去背」變成一句話的事。

3-12 MCP Workflow Deep Dive：Claude Code ↔ MCP Server補充

一次工具呼叫背後的完整流程（訊息格式為 JSON-RPC 2.0）：

  1. 啟動：Claude Code 依設定啟動 server 程序（stdio），或連到遠端 URL。
  2. initialize：雙方交換協定版本與支援的能力。
  3. tools/list：取得每個工具的名稱、描述、參數 JSON Schema，放進模型的脈絡。這就是 MCP 佔脈絡的來源。
  4. 模型決策：你下 prompt，模型根據工具描述判斷要不要用、用哪個、參數填什麼。
  5. 權限檢查：Claude Code 攔下這次呼叫，依你的權限設定放行或詢問。
  6. tools/call：送出請求，server 執行並回傳結果。
  7. 回到模型：結果進入對話，模型決定下一步，可能再呼叫、也可能回答你。

從這個流程得到的推論：

  • server 本身沒有 AI，它只是被呼叫的函式。模型看不到你的實作，只看得到描述與 schema，所以描述寫不好，工具就不會被用或被誤用。
  • 回傳內容會完整進入脈絡，回傳越肥，後續每一輪越貴。
  • 除錯先分段：用 Inspector 確認 server 本身正常，再用 /mcp 確認連線，最後才看模型為什麼不呼叫。

3-13 【MCP Server】客製化 MCP Server 實戰（SSE）：Icon Generator補充

stdio server 每個人都要在自己機器上裝一份。改成網路服務後部署一次、全隊連同一個網址，金鑰也只需要放在伺服器端。

import os, httpx
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("icon-generator", host="0.0.0.0", port=8000)

@mcp.tool()
async def generate_icon(description: str, style: str = "flat", size: int = 512) -> str:
    """依文字描述產生 App 圖示，回傳圖片網址。
    style 可為 flat、outline、3d；size 為邊長像素。"""
    # 呼叫你選用的圖片生成 API，金鑰留在伺服器端
    async with httpx.AsyncClient(timeout=120) as c:
        r = await c.post(os.environ["IMAGE_API_URL"],
                         headers={"Authorization": f"Bearer {os.environ['IMAGE_API_KEY']}"},
                         json={"prompt": f"{style} app icon, {description}", "size": size})
    return r.json()["url"]

mcp.run(transport="sse")
claude mcp add --transport sse icon-generator http://localhost:8000/sse
版本提醒：MCP 規格已把 SSE 傳輸列為舊式，新的標準是 Streamable HTTP。Claude Code 兩者都支援，新寫的 server 建議改用 mcp.run(transport="streamable-http")，端點是 /mcp，連接時用 --transport http。概念完全相同。

對外開放前要加認證（至少檢查 header 的 token）、限流，生成類 API 每次呼叫都是錢。

4-1 Hook 是什麼：事件驅動的 AI 工作流程補充

寫在 CLAUDE.md 的規則是建議，模型可能忘記或判斷不適用。Hook 是在固定生命週期點由系統執行的處理程式，不經過模型決定，結果是確定的。凡是「每次都必須發生」的事就該用 Hook。

事件觸發時機常見用途
PreToolUse工具執行前，可阻擋擋危險指令、保護檔案、檢查規格
PostToolUse工具執行後格式化、lint、跑測試
Notification需要你注意時音效、桌面或手機通知
StopClaude 準備結束回合完成通知、品質關卡
UserPromptSubmit你送出 prompt 時掃描金鑰、附加脈絡
SubagentStopSub-Agent 結束驗收子任務
SessionStart工作階段開始載入分支、近期 issue 等資訊

運作方式：事件發生時，Claude Code 把事件資料以 JSON 從 stdin 傳給你的指令；你的指令用結束代碼回話。0 是通過，2 是阻擋並把 stderr 的內容回饋給 Claude，它會據此修正。設定放在 .claude/settings.json（團隊）或 ~/.claude/settings.json（個人），用 /hooks 檢視。

4-2 【Hook】Notification：即時事件通知補充

放著 Claude 跑長任務、自己去做別的事，回來才發現它十分鐘前就停下來等你按確認。通知 Hook 解決的就是這個。對應到兩個事件：Notification 在 Claude 等待你的輸入或權限時觸發；任務跑完的通知則掛在 Stop。

// ~/.claude/settings.json（個人偏好，放全域）
{
  "hooks": {
    "Notification": [{
      "hooks": [{ "type": "command",
        "command": "osascript -e 'display notification \"Claude 需要你\" with title \"Claude Code\"'" }]
    }],
    "Stop": [{
      "hooks": [{ "type": "command",
        "command": "osascript -e 'display notification \"任務完成\" with title \"Claude Code\"'" }]
    }]
  }
}

Windows 可用 PowerShell 的 BurntToast 模組或 msg，Linux 用 notify-send。想推到手機，就把指令換成 curl 打 ntfy、Slack 或 LINE 的 webhook；你熟的 n8n webhook 也可以當接收端，再分流到任何地方。stdin 的 JSON 裡有 message 欄位可以帶進通知內文。

要區分成功與失敗：Stop 只代表回合結束，不代表成功。可以在 Stop hook 裡自己跑一次測試，依結果發不同通知。

4-4 【Hook】PreToolUse：寫入前的規格與安全檢查補充

在 Write 或 Edit 真正落地前攔截。stdin 會收到 tool_name 與 tool_input：Write 有 file_path 與 content，Edit 有 file_path、old_string、new_string，所以路徑和即將寫入的內容都檢查得到。

#!/usr/bin/env python3
# .claude/hooks/pre_write.py
import json, re, sys

d = json.load(sys.stdin)
ti = d.get("tool_input", {})
path = ti.get("file_path", "")
text = ti.get("content") or ti.get("new_string") or ""

def block(msg):
    print(msg, file=sys.stderr); sys.exit(2)   # 2 = 阻擋，訊息回饋給 Claude

# 安全：受保護路徑
if any(s in path for s in (".env", "secrets/", "migrations/2")):
    block(f"禁止修改 {path}。已存在的 migration 不可變更，請新增一支。")

# 安全：疑似金鑰
if re.search(r"(sk-[A-Za-z0-9]{20,}|AKIA[0-9A-Z]{16}|-----BEGIN .*PRIVATE KEY)", text):
    block("內容疑似含有金鑰，請改用環境變數。")

# 規格：專案慣例
if path.endswith((".ts", ".tsx")) and re.search(r":\s*any\b", text):
    block("專案規範禁止使用 any，請給明確型別。")
"PreToolUse": [{
  "matcher": "Write|Edit",
  "hooks": [{ "type": "command",
    "command": "python3 \"$CLAUDE_PROJECT_DIR\"/.claude/hooks/pre_write.py" }]
}]

阻擋訊息要寫「為什麼」與「該怎麼做」，Claude 會照著改。對 Bash 也可以掛同樣的檢查，擋 rm -rf、git push --force、對正式環境的指令。Hook 要快，幾百毫秒內結束，否則每次寫入都卡。

4-5 【Hook】PostToolUse：寫入後的自動化測試啟動補充

檔案寫入後自動跑檢查，失敗就把錯誤回饋給 Claude，它會立刻修。這把「記得跑測試」從期望變成機制。

#!/bin/bash
# .claude/hooks/post_write.sh
f=$(jq -r '.tool_input.file_path')

case "$f" in
  *.ts|*.tsx)
    npx prettier --write "$f" >/dev/null 2>&1
    out=$(npx vitest related "$f" --run 2>&1) || {
      echo "$out" | tail -40 >&2     # 只回饋尾段，避免灌爆脈絡
      exit 2
    } ;;
esac
"PostToolUse": [{
  "matcher": "Write|Edit",
  "hooks": [{ "type": "command",
    "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/post_write.sh" }]
}]
  • 只跑相關測試（vitest related、jest --findRelatedTests、pytest 指定檔案）。每次編輯跑全套會慢到無法工作。
  • PostToolUse 無法撤銷已發生的寫入，exit 2 的作用是通知 Claude 有問題。
  • 完整測試套件適合放在 Stop：Claude 想收工時跑一次，沒過就 exit 2 擋下，它會繼續修。腳本要檢查輸入中的 stop_hook_active，已經是被擋回來的那一輪就放行，避免無限循環。

4-6 Sub-Agent 是什麼：多 Agent 協作模型補充

Sub-Agent 是擁有獨立脈絡視窗、專屬 system prompt 與工具權限的子代理。主對話像主管：派任務、收結論，不看過程。

  • 脈絡隔離：子代理讀了五十個檔案、跑了三百行測試輸出，主對話只收到一段摘要。
  • 權限收斂：reviewer 不給寫入工具，它就不可能亂改。
  • 專業化：每個角色有自己的指示與檢查清單，也可以指定較便宜的模型。

內建的有 Explore（唯讀、快速搜尋）、Plan（Plan Mode 下做研究）、general-purpose。自訂的放 .claude/agents/，用 /agents 建立與管理。

<!-- .claude/agents/code-reviewer.md -->
---
name: code-reviewer
description: 程式碼審查。完成一段程式修改後主動使用。
tools: Read, Grep, Glob, Bash
model: sonnet
---
你是資深 reviewer。執行 git diff 檢視變更，依序檢查：
1. 邏輯錯誤與邊界條件
2. 安全問題（注入、金鑰外洩、權限檢查遺漏）
3. 是否有對應測試
4. 是否符合 CLAUDE.md 的慣例
依「必須修、建議修、可忽略」分級回報，每項附檔名與行號。

限制要知道：子代理從零開始，不知道主對話談過什麼，派工時的任務描述必須自足；子代理不能再派子代理；description 決定 Claude 何時自動委派，要寫明觸發情境。

4-7 【Sub-Agent】多線程模式：多 Agent 並行處理補充

同一則訊息裡派出的多個子代理會同時執行。關鍵是任務之間要獨立、不改同一批檔案。

同時派三個 sub-agent 分別調查，每個只回報結論與相關檔案路徑：
1. 前端：購物車狀態怎麼管理、在哪些元件被讀寫
2. 後端：訂單 API 的驗證與錯誤處理現況
3. 資料庫：orders 相關的 schema、索引、既有 migration
全部回來後，彙整成「加入優惠券功能」的實作計畫。
模式做法適合
平行探索多個唯讀 agent 各查一塊再彙整熟悉大型 codebase、根因調查
流水線實作 → reviewer → test-runner 依序接力有固定品質關卡的開發
多視角審查安全、效能、可讀性各一個 reviewer 同時看重要 PR
平行實作各自在獨立 git worktree 改不同模組互不相依的功能或批次遷移

平行寫入同一個工作目錄會互相覆蓋，要寫就用 worktree 隔開（git worktree add ../proj-feature-a -b feature-a），或用內建的 /batch 讓它自動拆分。成本也要算：每個子代理都有自己的脈絡，三個平行就是三份用量，拿來換的是時間與主對話的乾淨。

4-8 Skill 是什麼：動態 Context 載入機制補充

把所有流程與規範都塞進 CLAUDE.md，每次對話都要付這筆脈絡費，而且規則一多模型就抓不到重點。Skill 用三層漸進載入解決：

  1. 常駐：只有 name 與 description，每個 Skill 幾十個 token。
  2. 觸發時：Claude 判斷當前任務相關，才讀入 SKILL.md 全文。
  3. 需要時：SKILL.md 裡提到的附檔（範本、參考文件、腳本）用到才讀或執行。
.claude/skills/
└── release-notes/
    ├── SKILL.md            # 必要：frontmatter + 指示
    ├── templates/release.md
    └── scripts/collect.sh  # 腳本直接執行，內容不佔脈絡

學員評價提到「AI 常忘了曾經寫過的 skill」，原因幾乎都在 description：它是唯一的觸發依據，要同時寫出「做什麼」與「什麼時候用」，並包含使用者會說的字眼。名稱用小寫加連字號、看得出用途。Skill 也可以用 /skill名稱 手動叫用。

4-9 【Skill】以規則約束 AI：資料庫設計原則的強制落地補充

schema 一旦上線就很難改，而 AI 每次設計資料表的風格都可能不同。把團隊的資料庫規範做成 Skill，凡是碰到 schema 的任務都會先載入。

<!-- .claude/skills/db-schema-rules/SKILL.md -->
---
name: db-schema-rules
description: 資料庫設計規範。新增或修改資料表、撰寫 migration、設計 schema、調整索引時必須使用。
---
# 設計原則
- 表名 snake_case 複數；主鍵一律 `id`
- 每張表必有 created_at、updated_at；需要保留紀錄的表用 deleted_at 軟刪除
- 金額存整數（最小貨幣單位），禁止 float
- 外鍵必加索引，並明確指定 ON DELETE 行為
- 列舉值用 CHECK 或對照表，不用魔術數字
- 已合併的 migration 不可修改，一律新增

# 流程
1. 先列出變更內容與對既有資料的影響，等我確認
2. 撰寫 migration，必須包含可回復的 down
3. 執行 scripts/check_schema.sh，全數通過才算完成

命名細節與範例見 reference/naming.md

要注意「強制」的程度：Skill 仍然是給模型的指示，屬於強力建議。真正做到強制，是把可機械檢查的部分寫成腳本，再用 4-4、4-5 的 Hook 在寫入 migration 時執行。Skill 負責讓它第一次就做對，Hook 負責保證做錯時過不了關。

4-10 【Plugin】從個人到團隊：共享 Custom Commands補充

把 .claude/ 提交進 repo 只能在單一專案共用。Plugin 把 commands、agents、skills、hooks、MCP 設定打包成一個可安裝、有版本的單位，跨專案、跨團隊發佈。

team-tools/
├── .claude-plugin/plugin.json     # {"name":"team-tools","version":"1.0.0","description":"…"}
├── commands/deploy-vercel.md
├── agents/code-reviewer.md
├── skills/db-schema-rules/SKILL.md
├── hooks/hooks.json
└── .mcp.json

發佈靠 marketplace：一個 git repo，根目錄有 .claude-plugin/marketplace.json 列出有哪些 plugin。

/plugin marketplace add your-org/claude-plugins
/plugin install team-tools@your-org
# 安裝後指令帶命名空間
/team-tools:deploy-vercel prod

在專案的 .claude/settings.json 設定 extraKnownMarketplaces 與 enabledPlugins，同事信任該專案資料夾後就會被提示安裝，新人到職不必逐項設定。Plugin 可以夾帶 Hook 與 MCP server，等同可執行的程式，只裝來源可信的，內部 marketplace 的 repo 也要走 code review。

5-4 團隊導入：AI-First 的開發流程設計補充

階段AI 負責人負責
需求討論整理會議內容、列出模糊點與邊界情況決定做什麼、不做什麼
任務拆解讀 codebase 後提出計畫與影響範圍審計畫、定優先順序
實作寫程式與測試，自我驗證適時打斷、修正方向
Reviewreviewer 子代理先做第一輪看設計是否合理、AI 容易漏的業務脈絡
測試跑測試、E2E、修失敗項驗收、探索性測試

需求拆解的方法

  • 依「垂直切片」拆：每一片都是可執行、可驗收的小功能，而不是「先把所有 API 寫完」。
  • 每一片寫驗收條件並指定驗證方式（哪個測試、哪個指令、畫面上看到什麼）。
  • 規格與進度寫成 markdown 檔放在 repo，人和 AI 讀同一份。

哪些交給 AI、哪些要人確認

  • 可放手：樣板程式、測試補齊、重構、文件、型別修正、依既有模式新增的 CRUD。
  • AI 做、人必審：商業邏輯、對外 API 變更、效能敏感路徑。
  • 人主導：認證授權、金流、資料庫 migration、基礎設施設定、任何刪除資料的操作。

導入步驟

  1. 把 CLAUDE.md、.claude/settings.json、agents、skills、.mcp.json 提交進 repo，全隊的 Claude 拿到同一份脈絡與規則。
  2. 從低風險處開始：測試與文件，再到 bug 修復，最後才是新功能。
  3. 責任講明：誰提交誰負責，不論程式是誰寫的。AI 產出的 PR 一樣要小、要有測試、要有清楚描述。
  4. 每週收集「Claude 又犯了什麼錯」，轉成 CLAUDE.md 規則、Skill 或 Hook。設定會越用越準。

5-5 資安與權限控管實務補充

不該進入對話的資料

  • 金鑰、token、密碼、憑證檔
  • 真實客戶個資與正式環境資料庫內容
  • 合約或法規限制不得外流的原始碼與文件（先確認公司政策與所用方案的資料保留條款）

權限設定

// .claude/settings.json，進 git 全隊一致
{
  "permissions": {
    "allow": ["Bash(npm run test:*)", "Bash(git diff:*)", "Bash(git status)"],
    "deny":  ["Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)",
              "Bash(git push:*)", "Bash(rm -rf:*)", "Bash(curl:*)"]
  }
}

權限模式用 Shift+Tab 切換：預設（每項詢問）、自動接受編輯、Plan（唯讀）。規則的優先順序是 deny 高於 allow。

多層防護

  1. 權限 deny：擋敏感路徑的讀取與不可逆指令。
  2. PreToolUse Hook：如 4-4，檢查路徑、內容中的金鑰樣式、危險指令。
  3. UserPromptSubmit Hook：掃描你貼進 prompt 的內容是否含金鑰，有就擋下。
  4. 最小權限：給 Claude 用的資料庫帳號設唯讀、雲端憑證限縮範圍、不要在有正式環境憑證的 shell 裡跑。
  5. 隔離環境：--dangerously-skip-permissions 只在沒有機密、網路受限的容器裡用；也可啟用沙箱模式限制檔案與網路存取。
  6. 供應鏈：第三方 MCP server、Plugin、Hook 都是會執行的程式，只裝可信來源。會讀取外部內容的工具（網頁、issue、錯誤訊息）可能夾帶 prompt injection，不要同時開放高風險權限。
  7. 企業管控：管理員下發 managed settings，統一強制權限與 Hook，使用者無法覆蓋。
